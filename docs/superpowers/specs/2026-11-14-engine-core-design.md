# dk_voxel engine core — design

Project 1 of 3 in turning the dk_voxel tech demo into an addon reused across the user's own games.
Project 2 (authoring and bake) and project 3 (moving and breakable voxel objects) build on this one and are
designed later; this document only notes what they need from the core.

## Intent

Today `VoxelWorld` is a fixed box created from script (`create(size_in_chunks, cell_size)`), filled by one
hard-coded terrain generator, viewed from the active camera only, with materials defined as a dictionary in
`demo/main.gd`. Nothing is saved. That is a good demo and a poor base for games.

the user will build several games on this engine:

- **Endless worlds** (Minecraft-like in scope, smooth dual-contoured terrain, not cubes): procedurally
  generated by game-specific C++ rules, with hand-made structures stamped in, and player changes saved.
- **Hand-made levels** (Donkey Kong Bananza-like): bounded, authored in the editor, baked, and loaded.

Both run on one engine. The core has to stream an unbounded world, take each game's own generator, follow
whatever needs terrain loaded (not just the camera), save what players change, and tell the game when terrain
changes.

## Goals

1. **Unbounded streaming storage.** Chunks load around viewers and unload behind them. A bounded world is the
   same storage with limits.
2. **Pluggable C++ generators**, one or more per game, configured in the inspector.
3. **Several viewers.** LOD, loading and collision follow any `VoxelViewer` node (player, NPC, physics object),
   not only the camera.
4. **Saving player changes.** Only edited chunks are written. An unloaded edited chunk comes back exactly as
   left.
5. **Change events** so audio, AI, quests and gameplay can react to edits.
6. **Material sets as resources** (look and hardness in one place) instead of demo-script dictionaries.
7. **Works within about 8 km of the origin** (the user's decision). Stock single-precision Godot makes the camera,
   player and physics jitter further out, whatever the voxel code does. Upgrade path when a game needs more: a
   `precision=double` build of Godot and godot-cpp. Origin shifting was considered and not chosen, because every
   game would have to cooperate with it.

## Non-goals

- Editor authoring, mesh voxelization, baking, structure stamps (project 2). The core only provides the hooks
  listed under *What projects 2 and 3 need*.
- Moving or breakable voxel objects (project 3).
- A cube or Minecraft-block mesher. Smooth dual contouring only.
- Public-addon polish: builds for every platform, API-stability promises, user docs beyond the README.
- Automatic separation of terrain that gets cut loose.
- Far-distance terrain beyond the LOD2 ring (impostors, larger LOD chunks). View distance is limited by what
  the three existing LODs can stream.
- Networking or multiplayer sync.
- Streaming or rendering in the editor viewport (my call). In the editor, as today, nothing is meshed. Editor
  preview belongs to project 2 (authoring), which needs it anyway.

## Anti-goals (a failure even if it works)

- Regressing the mesher: seams between chunks must stay bit-exact for any LOD mix, and ms/chunk must not get
  worse. `selftest` and `tests/run_tests.gd` must keep passing.
- Holes or pop-in close to the player while walking or sprinting. Streaming must stay ahead of the viewer.
- A generator API that forces per-voxel virtual calls or Godot calls on worker threads.
- Saves that lose edits: an edited chunk that unloads and reloads must come back exactly as left.
- Abstraction for its own sake. Split the code only where a new feature needs it.

## Constraints

- Godot 4.7, godot-cpp pinned in `build.sh`, C++17, Jolt physics, SCons. Linux x86_64 and macOS arm64 as today.
- `voxel_core` stays free of Godot (host-built `selftest`).
- Keep the voxel format, 2 bytes per voxel (density, material), with optional Hermite data per 8³ block. It
  matches Bananza and project 2 depends on it.
- Chunk = 16³ cells = 2³ blocks of 8³ voxels (`CHUNK`, `BLOCK`). The mesher reads samples −2..17 around a chunk,
  so a chunk can be meshed only once all 26 neighbours have data.
- Edits are main-thread calls (as today); meshing and generation run on worker threads.

## Approaches considered

### How each game's C++ generator plugs in

- **A. The game compiles the addon's source into its own library (chosen).** Each game repo includes
  `dk_voxel` as a git submodule. The game's SConstruct builds the addon sources plus its own generators into a
  single GDExtension. Generators are ordinary C++ subclasses called directly on worker threads. Cost: no
  prebuilt drop-in addon. That is fine for one developer's own games.
- B. Prebuilt addon plus a per-game library that registers generators through a C function table. Keeps
  binaries separate, but the hand-rolled ABI breaks silently when structs change. Only worth it for third-party
  users.
- C. Generator as a Godot class with an overridable virtual (GDScript or another extension). Allows GDScript
  prototyping, but every call goes through Godot's dispatch and copies buffers, and godot-cpp cannot cleanly
  subclass another extension's class. Dropped.

### How endless storage works

- **A. Sparse map of chunks keyed by chunk coordinate (chosen).** Created when generation reaches them,
  dropped when no viewer needs them, written to the save if edited. A bounded level is the same map with
  limits. The mesher, edits and LOD logic stay the same; only how voxels are looked up changes.
- B. Sliding window: today's fixed array with wrapped coordinates, re-centred on the player. A smaller diff, but
  view distance and height are fixed, several viewers in different places cannot work, and bounded levels need
  a second path. That works against one engine for both kinds of game.

## Design

### Storage (core, Godot-free)

- `Volume` becomes a map from chunk coordinate (`int32 x, y, z`) to a chunk: 8 blocks, each uniform (one voxel
  value) or dense (512 voxels + optional Hermite), as blocks are today.
- Optional **bounds** in chunks. Empty bounds = endless on all three axes. Outside the bounds reads as air, so
  a bounded world stays closed on every side as it is today. Inside the bounds, a chunk that is not loaded is
  "unknown", not air. The mesher never runs next to unknown chunks.
- **Bounded worlds load completely and never unload** (my call). On entering the tree, or on the first edit or
  query, every chunk is filled synchronously from its source, as `generate_terrain` does today. So setup
  scripts (the demo's `_build_ruins`, the test's slab) edit and raycast right away. Small bounded worlds
  (project 3's voxel objects) stay resident. Viewers only drive LOD, meshing and collision for them. Streaming
  and unloading apply to endless worlds only, and the clip-to-loaded rule for edits only affects endless worlds.
- Chunk states: *absent → generating → ready*. Ready chunks carry `modified` (needs saving) and a version
  counter (for remeshing, as today).
- Chunk data sources, in priority order: **save file → baked data (project 2) → generator → air**.
- Thread safety: keep the single `shared_mutex` over the map and voxels.
  `// ponytail: one global lock; per-chunk locks if workers contend.`

### Generators

```cpp
namespace dkv {
struct Generator {
    virtual ~Generator() = default;
    // Fill one 8^3 block. origin = voxel coordinate of the block's corner, cell = metres per voxel.
    // Must be thread-safe, const, and deterministic in (settings, origin): unloaded chunks are regenerated.
    virtual void generate_block(const int origin[3], float cell, Voxel out[512]) const = 0;
};
}
```

- The engine detects uniform blocks itself (as `generate()` does today), so generators just fill arrays.
  `// ponytail: per-block calls; add a per-column or per-chunk hook if generators need shared column data
  (heightmaps) and profiling shows the recomputation hurts.` Today's generator computes 64 heights per block
  column. The builder should check whether a per-chunk-column cache is needed to keep today's speed, and add
  it only then.
- Godot side: addon class `VoxelGenerator : Resource`, holding the `dkv::Generator`. A game subclasses it in its
  own C++ (same library, same godot-cpp, so plain C++ inheritance works), exports its settings as normal
  properties, and registers it in its own `initialize` function. `VoxelWorld.generator` holds the resource, so
  each world picks and tunes its generator in the inspector.
- Today's hills/caves/ore terrain moves out of `Volume` into `DemoTerrainGenerator`, shipped with the addon as
  the example and used by the demo.

### Viewers, streaming and LOD

- New node `VoxelViewer : Node3D` with `view_distance`, `vertical_view_distance`, `collision_distance`,
  `enabled`. Viewers register with every `VoxelWorld` in the same `World3D`.
- If no viewer exists, the active camera acts as one with the world's defaults, so simple scenes and the
  existing test keep working.
- Per scan (as today: when a viewer crosses a chunk boundary, or after edits):
  - wanted set = chunks within any viewer's distance (plus a one-chunk margin so neighbours exist for meshing)
  - generate missing ones, nearest first
  - mesh a chunk once it and its 26 neighbours are ready
  - LOD from the nearest viewer's distance, with today's hysteresis
  - collision for chunks within any viewer's `collision_distance`
  - unload chunks beyond every viewer's distance plus hysteresis; write modified chunks to the save first
- Job priority: edits to chunks on screen first (as today), then by distance to the nearest viewer, with
  generation of chunks needed by an already-wanted mesh ahead of new ones.
- **Precision:** mesh and collision vertices are relative to the chunk origin, and each chunk's render
  instance and body carry the chunk offset. That keeps mesh data precise and would carry over to a
  double-precision build unchanged. It does not fix camera or physics jitter beyond about 8 km (see goal 7).
  Core voxel coordinates are `int32`, which is far more range than 8 km needs.
- Bounded worlds keep `lod1_distance` / `lod2_distance` / `collision_distance` as world properties. Viewer
  distances decide what is loaded; world distances decide the LOD bands.

### Saving

- `VoxelWorld.save_directory` (e.g. `user://saves/slot1/overworld`). Empty = nothing goes to disk, but edits
  are never lost while the world exists (my call): modified chunks that unload are kept serialised (compressed)
  in an in-memory store and restored from it. The unload path is the same either way; only the store differs.
- **What a save belongs to is the game's job** (my call). The header holds format version, cell size and
  generator class name, and a mismatch on any of those is rejected with an error. Seed and other generator
  settings are not checked. Games give each world or seed its own directory. `reset()` clears the in-memory
  store and never deletes files. A game starting a new world points `save_directory` somewhere new first.
- An edited chunk is marked `modified`. It is written when it unloads, and on `save()` (writes every modified
  loaded chunk; the game calls it at checkpoints and on quit).
- When loading, the chunk's file is used instead of baked or generated data.
- Format (my call): one compressed file per modified chunk, blocks plus Hermite, with a small header (format
  version, cell size, generator class name). File I/O lives on the Godot side (`FileAccess`, zstd); the core
  only serialises a chunk to and from bytes.
  `// ponytail: one file per chunk; pack into region files if file counts become a problem.`
- A save written with a different cell size is rejected with an error, not loaded.

### Events

- Signal `terrain_edited(aabb: AABB, result: Dictionary)` after every edit call. `result` is what the edit
  methods return today (`changed`, `removed` m³ per material, `volume`).
- `is_area_ready(aabb, need_collision := true) -> bool`, so games can hold spawns until terrain and colliders
  exist. This replaces the demo's polling of `get_stats()`.
- No per-chunk load/unload signals until a game needs them.

### Materials

- `VoxelMaterialDef : Resource`: `name`, `color_a`, `color_b`, `pattern_scale`, `roughness`, `metallic`,
  `emission`, `hardness`.
- `VoxelMaterialSet : Resource`: an array of defs, where the index is the material id.
- `VoxelWorld.material_set`: sets hardness in the core and fills the terrain shader's arrays when `material`
  is a `ShaderMaterial` using `voxel_terrain.gdshader`. A game with its own shader can ignore the set's look
  fields.
- The shader supports 16 materials (`& 15`). Raise it to 32 while moving this code. The data format supports 256.

### API changes

- `create(size, cell, threads)` and `generate_terrain(seed)` are replaced by properties: `cell_size`,
  `bounds` (AABB in chunks; zero size = endless), `generator`, `material_set`, `save_directory`, `threads`.
  The world starts streaming when it enters the tree. `reset()` drops all chunks (the demo's "new world").
- The edit, query and stat methods keep their names and behaviour (`dig_sphere`, `build_box`, `raycast`,
  `get_density`, `get_stats`, …).
- Edits that reach chunks that aren't loaded are clipped to loaded chunks (my call). `result.changed` reflects
  only what was applied.
  `// ponytail: edits outside loaded chunks are dropped; queue them per chunk if a game needs remote edits.`
- The demo and `tests/run_tests.gd` are updated to the new API. No compatibility shims.

### Code layout

- Core: split storage/streaming out of the mesher, because storage changes heavily and the mesher shouldn't
  have to change with it. Likely `volume.*` (map, edits, queries, serialisation), `mesher.cpp`,
  `generator.h`, `demo_generator.cpp`. The builder decides the exact split.
- Godot side: `voxel_world.cpp` keeps the node and API. Scheduling, rendering/collision upload, viewers, and
  resources go in their own files once they grow.
- The build: today's SConstruct plus a documented way for a game's SConstruct to include the addon sources
  (one function or SConscript the game calls with its own source list).

## Projects 2 and 3, as discussed so far

These are not designed yet. Each gets its own brainstorm and design doc once this one is built. This section
records what was agreed, so the core doesn't close those doors.

### Project 2: authoring and bake

Modelled on how Donkey Kong Bananza builds its levels. That was found by reading the game's data: stage
placement files, voxel part definitions, baked voxel files.

- **How Bananza does it:** Terrain parts are modelled as meshes (Maya) and voxelized offline, one distance
  field per material. In the level editor, designers place **voxel field** boxes (bounds, cell size, LOD
  and material settings) and an ordered list of operations, each with a **priority**:
  - placed mesh parts: add, erase, or paste over; optionally "becomes a separate object"
  - cube and cylinder add/erase primitives
  - material-swap zones
  An offline bake merges everything into voxel data per field and per story scenario, and the game loads
  that, not the operation list. No freehand sculpting.
- **What the user wants:** the same approach, with **Blender** instead of Maya. Godot imports `.blend`/`.glb`
  itself, so the addon converts imported meshes to voxels inside Godot, and each Blender material slot maps to
  a voxel material. No Blender add-on.
- **Proposed shape:**
  - In a Godot scene, place a voxel field node and fill it with nodes: mesh part (add / erase / paste over),
    box / cylinder / sphere shape (add / erase), material-swap zone. Each has a priority.
  - A bake merges them into voxel data saved next to the scene. The core loads it as the "baked data" source.
  - The bake re-runs when a node changes (a button at first is fine), with the result shown in the editor
    viewport. Editor streaming and preview belong to this project.
- **Structures for endless worlds** are the same node setup saved as their own scene and baked into a small
  voxel stamp. A game's C++ generator places stamps while generating chunks. Stamps can span chunk borders.
- **Not included:** freehand sculpting brushes, a Blender add-on, Bananza's per-scenario level variants (can be
  added later with separate baked files).

### Project 3: moving and breakable voxel objects

- **Moving objects:** small bounded voxel volumes, animated (rotate, follow a path) or physics-driven, that
  the player can still dig. Most likely each is a small bounded `VoxelWorld` with its own transform.
- **Breakable objects:** authored in the level (a part marked "becomes a separate object"). They break into
  fragments or come loose.
- **Support-watching parts:** terrain carries an "anchored ground" mark. A part can opt in to watch whether the
  anchored ground holding it is destroyed, and fall when it is. This matches what Bananza appears to do
  (`IsObservePartsGroundBreak`, `RemoveFixedGroundAttribute` in its placement data).
- **Not included:** automatic separation of arbitrary terrain that gets cut loose. the user confirmed authored
  objects and support-watching parts are enough. Bananza shows no sign of a general version either.

## What projects 2 and 3 need from the core

- A baked-data source per chunk (slot reserved in the source order above).
- Several `VoxelWorld`s in one scene, each with its own transform. Already true today; must stay true, because
  voxel objects (project 3) will probably be small bounded worlds.
- Per-voxel room for an "anchored ground" flag (Bananza's fixed-ground attribute) for support-watching parts.
  *Not built here.* The builder only checks that the save format has a version number so the flag can be
  added later.
- Generators able to stamp structures that span chunks. *Not built here.* Project 2 designs it. The
  deterministic per-block contract above has to stay compatible with it, for example by structures being
  placed from hashed region coordinates.

## Testing

- `selftest` (core, no Godot):
  - seams stay bit-exact across chunk borders and LOD mixes with a generator
  - generation is deterministic
  - chunk serialise → deserialise round-trips exactly, Hermite included
  - edits clip correctly at unloaded chunks
- `run_tests.gd` (Godot):
  - existing ball/dig/build/hardness checks, ported to the new API
  - a second viewer far from the camera gets collision (a ball resting there)
  - dig, unload by moving the viewer away, return, and the crater is still there (save round-trip)
- Demo: walking and flying through an endless `DemoTerrainGenerator` world has no holes near the player; the
  HUD still shows ms/chunk and the queue.

## Left to the builder

- Hash map choice, job-queue details, exact unload hysteresis and margins.
- File split inside the core and the node.
- Compressed save layout details (header fields beyond those listed, compression level).
- Whether `DemoTerrainGenerator` needs a per-column cache to keep today's generation speed.
- Default viewer distances. Viewer `collision_distance` decides collision; the world's value is the default
  for the camera fallback.
